# 2026 오픈소스 개발자대회 결과보고서 편집 설계

## 목표와 산출물

- 원본 DOCX는 변경하지 않고 별도 수정본 DOCX를 만든다.
- 붙임을 제외한 본문을 정확히 5쪽으로 맞춘다.
- 기존 사실과 성과는 최대한 보존하되, 중복·홍보성 통계·심사와 무관한 장문을 줄인다.
- 처음 보는 심사위원이 필요성, 구현 차별점, 검증 결과, 오픈소스 완성도를 빠르게 파악하도록 재구성한다.
- `docx-style-guide`는 적용하지 않는다. 기존 대회 양식의 표 구조와 옅은 청색 계열은 유지한다.

## 편집 방향

선택안은 **근거 중심형(B)**이다. 각 절은 주장보다 증거가 먼저 보이도록 `문제 → 해결 방식 → 실측 결과 → 오픈소스 완성도` 순서로 전개한다. Gartner 시장 통계와 중복 문장은 삭제하고, 프로젝트 자체 실험과 공개 저장소 증거를 중심으로 설득한다.

## 본문 5쪽 구성

1. **프로젝트 개요와 필요성**: 한 문장 정의, 사용자 문제, 기존 수동 튜닝의 한계, FiTuna의 해결 방식과 핵심 성과 요약.
2. **핵심 기능과 구조**: 계층형 아키텍처 도식, 계층별 한 줄 설명, 주요 파일명. 도식의 하단에는 역할 설명과 실제 파일명만 표시한다.
3. **구현 내용과 차별성**: 탐색·벤치마크·품질 검증 흐름, 안전장치와 재현성, 기존 방식 대비 차이. 명령 예시는 필수 동작만 남긴다.
4. **실측 검증과 경쟁력**: 동일 조건의 속도 비교 그래프와 실험 조건·결과·해석 본문. 그래프가 본문 설명을 대체하지 않도록 한다.
5. **오픈소스 완성도와 향후 계획**: 공개 배포, 테스트·CI, 문서화, PR·이슈·마일스톤 성과, 확장 계획을 심사 항목에 맞춰 압축한다.

## 아키텍처 도식

- 선택안: 계층형 요약 도식.
- 각 계층은 쉬운 한국어 제목과 한 문장 역할 설명을 가진다.
- 모듈 증거는 `hardware.py`, `binaries.py`, `model_info.py`처럼 실제 파일명만 표기한다.
- 장식보다 계층 흐름과 읽기 순서를 우선하며, 작은 셀에서도 읽히는 글자 크기와 대비를 확보한다.

## 실측 검증 표현

제목과 동일 실험 조건은 선명한 워드 본문 텍스트로 두고, 그래픽에는 막대 3개, 평균과 오차 범위, 모델별 설정값, 3회 중 목표 통과 횟수, 30 tok/s 목표선과 축 단위를 남긴다. 목표선 라벨은 막대를 가리지 않도록 최상위에 배치한다. 그래프 내부 최소 글자는 최종 삽입 크기에서 약 9pt 이상을 확보한다. 품질손실, 결과 해석, Gemini 제외 사유는 그래프 아래의 편집 가능한 본문 텍스트로 분리한다.

본문은 다음 정보를 유지한다.

- Qwen3-4B, Apple M3 Pro 18GB, llama.cpp build 9960, 설정별 3회 독립 실행이라는 동일 실험 조건.
- Claude 제안 30.49±0.88 tok/s·2/3회 통과, ChatGPT 제안 28.92±1.37 tok/s·1/3회 통과, FiTuna 32.68±1.71 tok/s·3/3회 통과라는 결과.
- 품질손실은 모두 허용 한계 5% 이내이며 Claude 1.53%, ChatGPT 1.75%, FiTuna 1.75%라는 설명.
- FiTuna가 Claude보다 적은 GPU 오프로드(`ngl 33 < 36`)로 속도·품질 목표를 3회 모두 충족했다는 해석.
- Gemini 3.1 Pro는 설정을 제시하지 않아 그래프에서 제외했다는 주석.

## 사실관계 정리

- 공개 `main` 기준 테스트 수 256개를 사용한다. 로컬 작업 중인 미커밋 테스트는 집계하지 않는다.
- “오픈 이슈 8건”은 현재 상태와 맞지 않으므로 “v0.3.0 마일스톤의 이슈 8건 전건 처리”로 고친다.
- 공개 저장소 근거인 28개 병합 PR, Python 3.11/3.13 및 3개 OS CI, PyPI v0.2.0, MIT 라이선스, 17개 모듈 자체 점검을 활용한다.

## 붙임

- **붙임 1 SBOM**: 실제 사용 관계가 명확한 핵심 오픈소스 구성요소 위주로 정리한다. 독점 도구인 `nvidia-smi`, `system_profiler`는 오픈소스 SBOM 표에서 제외하고, 직접 사용·파일 형식·빌드·시험 의존성을 구분한다.
- **붙임 2 AI 모델 명세**: 모델을 제품에 내장·적용하지 않고 외부 모델을 성능 검증에만 사용하므로 공식 안내 Q5에 따라 삭제한다.
- 최종 분량은 본문 5쪽과 붙임 1의 2쪽, 총 7쪽을 목표로 한다.

## 검증

- 새 DOCX를 PDF와 페이지 이미지로 렌더링해 본문 5쪽, 총 7쪽인지 확인한다.
- 7쪽 모두 육안 검사해 표 잘림, 도식·그래프 글자 크기, 페이지 넘김, 고아 문장, 겹침을 점검한다.
- 원본 파일의 해시와 수정 시각이 바뀌지 않았는지 확인한다.
- 별도 수정본만 최종 산출물로 전달한다.
